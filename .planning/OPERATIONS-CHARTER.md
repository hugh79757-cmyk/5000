# 5000 Operations Charter

> **읽는 시점:** 이 저장소에서 어떤 작업이든 시작하기 전에 읽는다. 특히 "대량 수정", "배포", "규칙 INSERT/변경", "백업/복구" 작업 전 필수.

>
> **체크리스트와의 관계:** 이 헌장은 "왜(배경)"를 설명한다. 실제 작업 시 매번 강제되는 행동은 `.planning/phases/PHASE-64-rule-system-evolution/64-PREFLIGHT-CHECKLISTS.md`의 작업 유형별 체크리스트가 담당한다. 헌장 전체 대신 작업 유형에 맞는 체크리스트만 프롬프트에 삽입하여 사용한다.

## 1. 이 프로젝트가 뭔지 (한 줄)

5000은 50개 이상의 한국어/영어 블로그를 자동 생성·발행하는 중앙 컨트롤 파이프라인이다. LLM으로 글을 쓰고, Hugo 정적 사이트로 만들어 Cloudflare Pages에 배포하고, IndexNow로 검색엔진에 알린다. 하루에도 여러 번 발행이 일어나며, 한 번 배포된 글은 수정하지 않으면 그대로 라이브에 남는다.

**즉, 여기서의 "실수"는 글이 잘못된 채 수십 개 사이트에 배포되고, 검색엔진에 등록되고, 독자에게 읽히는 것을 의미한다.**

## 2. 규칙 카테고리별 존재 이유와 배경 사고

### C — 콘텐츠 무결성 (Content Integrity)

**무슨 문제를 막는가:** LLM이 생성한 콘텐츠와 프론트매터에 사람이 손을 대지 않으면 자연스럽게 발생하는 결함.

**배경 사고:**
- **C01 (곡선따옴표):** LLM이 한국어 따옴표로 "…" 대신 '…'나 "…"를 출력. YAML 파서가 이 문자를 처리하지 못해 Hugo 빌드 실패. 여러 블로그에서 반복 발생.
- **C02 (프론트매터 미종료):** 첫 `---` 이후 두 번째 `---`가 없으면 YAML 블록이 끝나지 않음. 전체 포스트가 파싱 불가 → 발행 실패.
- **C03 (본문 키 유출):** 프론트매터 키 라인(`title:`, `slug:` 등)이 본문에 그대로 출력. Hugo 렌더링에서 의도치 않은 텍스트 노출 + SEO 혼란.
- **C04 (프롬프트 누수):** LLM이 "생각해보자""Let's think step by step""We need to write" 같은 사고 과정을 본문에 그대로 출력. 독자가 LLM 프롬프트를 읽는 상황이 발생. 신뢰도 훼손.
- **C09 (문자열화):** `categories: ["추천"]`(정상 list) 대신 `categories: "['추천']"`(문자열화된 list)로 저장되면, Hugo 템플릿의 `range .Params.categories`가 실패해서 해당 섹션이 아예 렌더링되지 않음. Phase 63에서 laptop-hugo 16건 + health-hugo 11건 발견. 총 27건.

**이 카테고리가 없으면:** LLM이 생성한 글을 그대로 배포하게 되고, 프론트매터 깨짐·본문 오염·섹션 누락이 그대로 독자에게 노출된다.

**규칙 ID 참조:** 규칙 식별자는 `RULE-C01`, `RULE-C02` 등 `RULE-` 접두어를 붙여 사용한다. 문제 인스턴스는 `ISSUE-####`(예: `ISSUE-0001`) 형식으로 별도 네임스페이스를 사용한다.

### L — 링크 건전성 (Link Health)

**무슨 문제를 막는가:** 콘텐츠 안의 링크(크로스셀, 제휴, 외부, 이미지)가 깨졌거나 잘못됐는지.

**배경 사고:**
- **C07 (죽은 크로스셀 링크):** 정보핫 크로스셀 카드가 이미 삭제된 포스트를 가리킴. dead_links 53건 + dongnam 42건, 총 95건 발견. 독자가 클릭해도 404. 제휴 기회 상실.

**이 카테고리가 없으면:** 깨진 링크를 독자가 클릭하고, 제휴 수익이 누락되고, 블로그 신뢰가 떨어진다. C07은 정보핫 링크만 검사하므로, coupang 등 제휴 링크의 URL 오류는 현재 탐지 불가.

### P — 발행 정합 (Publishing Integrity)

**무슨 문제를 막는가:** 콘텐츠가 의도대로 발행되었는지. 발행 상태, 시각, 중복, 메타데이터 일관성.

**배경 사고:**
- **P05 (구 C05, draft:true):** draft로 설정된 글이 발행되면 독자에게 미완성 콘텐츠가 노출됨. **Phase 64 결정: C05는 P 카테고리로 이동.** 규칙 ID는 `RULE-P05`로 표기하되, 기존 C05와의 이력 연결을 위해 메타데이터에 `legacy_id: "C05"` 기록. severity CRITICAL(배포차단)은 유지.
- **C06 (mtime>배포):** 로컬에서 수정했지만 배포가 안 된 상태. 파일은 최신인데 라이브는 예전 버전. **Phase 64 결정: C06도 P 카테고리로 재분류.** 문서상 `RULE-P06`으로 표기.
- **Phase 63 health 저혈압 글:** 로컬 파일은 정상(C01/C02/C09 통과)이었지만, 라이브 og:title이 "건강기능식품 추천 가이드"로 불일치. 파일은 문제없는데 라이브가 틀림. **이 사고가 P/V 경계 사례다 — 로컬 검사 통과 ≠ 라이브 정상.**

**이 카테고리가 없으면:** "파일 검사 통과했으니 배포 OK"라고 생각하게 되고, 배포 누락·중복 발행·날짜 오류 등을 놓는다.

### V — 라이브-파일 일치 (Version Verification)

**무슨 문제를 막는가:** 로컬 파일이 정상이라도, 실제 라이브 사이트가 그 파일을 올바르게 서빙하고 있는지.

**배경 사고:**
- **C08 (placeholder):** 현재 구현되지 않음. 라이브 비교 API 연동 시 활성화 예정.
- **Phase 63 저혈압 글:** 로컬 파일은 C01/C02/C09 전부 통과. 하지만 라이브에서 HTTP GET으로 확인한 결과:
  - `<title>`과 `og:title`이 파일 title과 불일치
  - `og:description`에 프론트매터 키(`title:`, `date:` 등)가 누출된 형태로 서빙됨
  - 본문에 곡선따옴표가 존재함 (파일에는 없었음 — 라이브가 다른 버전을 서빙 중)
- **이 사고의 교훈:** 파일 검사만으로는 충분하지 않다. "파일 정상"이 "라이브 정상"을 보장하지 않는다.

**이 카테고리가 없으면:** "방금 배포했고 preflight 통과했으니 OK"라고 생각하지만, 실제로는 CDN 캐시·이전 버전·다른 빌드 결과물이 라이브에 남아 있을 수 있다. 이 격차는 V 카테고리가 메운다.

### S — 구조/SEO (Structure & SEO)

**무슨 문제를 막는가:** 콘텐츠가 검색엔진과 독자 경험에 적합한 구조를 갖추고 있는지.

**현재 상태: 미구현.** 이 카테고리 규칙은 아직 구현되지 않았다.

**왜 필요한가:** 현재 규칙은 "콘텐츠가 깨졌는가"만 본다. "콘텐츠가 검색과 독자 경험에 적합한가"는 보지 않는다. 이 때문에 Phase 63에서 "이미지 0개" 판정 시 실제 이미지 존재 여부를 판정 못 하는 맹점이 드러났다. S 카테고리는 이 격차를 메운다.

**후보 규칙 (미구현·관찰대상):**
- **S01: featureimage/cover 누락** — **Phase 64 결정: severity=WARNING.** 커버 이미지 누락은 클릭률/SEO 저하 요인이지만, 배포차단 수준은 아님. Nullable 여부와 사이트 기본값 정책 확인 필요.
- S02: H2 섹션 수 부족
- S03: description 부실/placeholder
- **S04: 내부링크 0개** — **Phase 64 결정: 강제수준=권장(WARNING).** 모든 글에 내부링크를 강제하지 않고, 있으면 좋은 권장 수준으로 운영. WARNING severity이지만 자동조치 없음(로그 기록만). Phase 25 크로스링크 퍼널 목적과 별개로, 개별 글에 내부링크가 필수는 아님.
- S05: JSON-LD 누락

## 3. 절대 원칙

### 원칙 1: 진본 경로 확인 우선

**무엇을:** 어떤 파일을 수정하기 전에, 그 파일이 config에 등록된 진본 경로인지 확인한다.

**왜:** Phase 61 이전에 `5000/CUAP/health-hugo`라는 죽은 복사본이 존재했다. config site_path는 `/Users/twinssn/Projects/cuap/health-hugo`를 가리키고 있었는데, 에이전트가 `5000/CUAP/health-hugo`의 파일을 수정했다. 진짜 진본은 수정되지 않았고, 죽은 복사본만 건드린 셈이 됐다. 이 사고로 91건의 재작성 작업이 무효화됐다.

**어떻게:** 수정 전 확인 리스트:
1. `config/blogs.d/{blog}.yaml`의 `site_path`를 읽는다.
2. 그 경로가 실제 존재하는지, 최근 수정된 파일이 있는지 확인한다.
3. `5000/CUAP/` 또는 다른 위치에 같은 이름의 죽은 복사본이 없는지 확인한다.
4. 의심스러우면: 해당 경로의 `.git` 리모트/최근 커밋/파일 inode를 확인한다.

### 원칙 2: 파괴적 작업은 백업→파일럿→검증→확대

**무엇을:** 대량 수정, 파일 삭제(rm), DB UPDATE/DELETE, 전 포스트 재작성, 배치 스크립트 실행은 파괴적 작업이다.

**왜:** 91건 재작성 사고는 "일괄 스크립트"로 전체 포스트를 한 번에 수정하려다 범위가 꼬인 사례다. 파일럿 없이 전체 적용하면, 잘못된 수정이 수백 건에 동시에 반영된다.

**어떻게:** 순서:
1. **백업:** git tag, 스냅샷, 파일 복사 등 되돌릴 수 있는 수단 확보.
2. **파일럿:** 1건만 먼저 수정. 수정 후 해당 파일의 프론트매터 전체를 다시 출력해서 중복 키·빈 값·문법 오류 확인.
3. **검증:** 파일럿 1건에 규칙을 다시 돌려서 통과하는지 확인. Hugo 빌드 가능하면 빌드.
4. **확대:** 방식 확정되면 나머지 적용. dry-run 먼저.

### 원칙 3: "일괄 스크립트/전수 재작성"은 위험 신호 — 반드시 파일럿 선행

**무엇을:** "for 루프 돌려서 다 고친다", "전수 교체한다", "한 번에 다 된다"는 접근은 위험 신호다.

**왜:** 범위가 클수록 잘못된 수식 하나면 피해도 크다. 스크립트는 인간이 한 줄씩 확인할 시간을 생략하게 만든다.

**어떻게:**
- 스크립트는 반드시 dry-run 옵션 먼저 (`--dry-run` 또는 `--check` 모드로 실제 변경 없이 결과만 출력).
- 변경 전/후 SHA 비교 또는 diff로 변경 범위 확인.
- 스크립트 출력은 사람이 읽을 수 있는 형태로 (무슨 파일이 어떻게 바뀌는지 명확해야 함).

### 원칙 4: 파일 통계만으로 판정 금지 — 라이브 대조 필수

**무엇을:** "포스트 274건 파싱 성공", "이미지 256개 발견", "위반 0건" 같은 숫자만으로는 실제 상태를 알 수 없다.

**왜:** Phase 63에서 "이미지 0개" 판정 시, 파일 통계만으로는 실제 이미지 존재 여부를 판정 못 했다. health 저혈압 글은 로컬 파일 검사는 전부 통과했지만, 라이브는 다른 버전을 서빙 중이었다.

**어떻게:**
- 가능하면 HTTP HEAD/GET으로 라이브 URL 확인.
- CDN 지연 의심 시 purge 고려.
- "파일 통계 N건 정상"은 "라이브도 정상"의 필요조건일 뿐 충분조건이 아니다.
- V 카테고리(V01~V03)가 이 격차를 메우기 위한 규칙이다.

### 원칙 5: 게이트 우회 금지

**무엇을:** `preflight_check`가 `blocked=True`를 반환하면 배포하지 않는다.

**왜:** preflight는 C01/C02/C04/C07/C09 등 CRITICAL 규칙이 걸리면 배포를 막는다. 이 게이트를 우회하면 오염된 콘텐츠가 라이브에 배포된다.

**어떻게:**
- blocked=True면 원인 확인 → 수정 → 재검사 → 통과 후 배포.
- "급하니까" "블로그 하나만" "이 규칙은 오탐이야"라는 이유로 우회하지 않는다.
- 우회해야 하는 상황이면 그 이유를 문서화하고 사용자 승인 기록을 남긴다.
- C 카테고리 CRITICAL 규칙(C01/C02/C04/C09 등)은 우회 대상 아님.

### 원칙 6: 규칙 변경/추가는 역검증 통과 후에만

**무엇을:** 신규 규칙을 추가하거나, 기존 규칙의 severity를 변경하거나, 조건을 수정할 때는 역검증(전건탐지 + 오탐0)을 먼저 통과시킨다.

**왜:** 오탐이 있는 규칙을 CRITICAL 배포차단으로 올리면, 정상 글을 막는 거짓 양성이 발생한다. 게이트가 막았는데 알고 보니 정상이었던 사례가 쌓이면 에이전트와 사람 모두 게이트를 신뢰하지 않게 된다.

**어떻게:**
- 신규 규칙: 단계 2(임시 관찰, WARNING) → 단계 3(역검증) → 단계 4(승격) 순서.
- 기존 규칙 완화: 완화 후 역검증으로 "완화해도 진짜 문제를 놓치지 않는지" 확인.
- 기존 규칙 강화: 강화 후 역검증으로 "강화해도 오탐이 급증하지 않는지" 확인.

**결정 반영 — 관찰기간 기본 7일:**
- 신규 규칙의 단계 2(관찰단계) 기본 관찰기간은 **7일**이다.
- 7일은 주간 사이클을 커버하는 최소 기간. 문제 발생 빈도와 심각도에 따라 조정 가능.
- 관찰 데이터가 충분치 않으면 단계 2를 연장한다.

**결정 반영 — 긴급 예외 조항 (라이브 사고 확인된 명백 critical):**
- **예외 조건:** 라이브에서 확인된 명백(clear-cut) critical 문제이며, 역검증(전건탐지+오탐0)을 통과한 경우
- **예외 효과:** 관찰기간(7일)을 거치지 않고 즉시 단계 3(역검증) → 단계 4(승격)로 진행 가능
- **역검증 필수:** 긴급 예외라도 역검증은 생략할 수 없음. 전건탐지 100% + 오탐 0건 확인 필수
- **기록:** 긴급 예외 적용 시 `logs/rule_feedback.jsonl`에 사유 + 역검증 결과 기록

---

### 원칙 6-2: 오탐/미탐은 에이전트 자동 기록, 승격/강등은 사람 승인

**무엇을:** 규칙의 오탐/미탐 발견 시 기록 주체와 승격/강등의 승인 주체를 구분한다.

**결정 반영:**
- **오탐/미탐 기록은 에이전트가 자동 기록한다.**
  - 에이전트가 게이트 통과/차단 결과를 판단할 때 오탐 또는 미탐 의심 케이스를 발견하면 `logs/rule_feedback.jsonl`에 자동 기록
  - 기록 형식: `{timestamp, type, blog_id, slug, rule_id, severity, gate_decision, reason, detected_by: "agent"}`
  - 사람 승인 불필요: 오탐/미탐의 **기록 자체**는 에이전트가 자율적으로 수행

- **규칙의 severity 변경(WARNING↔CRITICAL↔MAJOR) 또는 승격/강등은 사람 승인이 필수다.**
  - 에이전트는 오탐/미탐 기록과 규칙 조건 조정 제안까지 수행 가능
  - 실제 severity 변경 또는 승격/강등 실행은 사람의 명시적 승인 후 진행
  - 승인 요청 시: 어떤 규칙의 어떤 severity를 어떻게 변경할지, 변경 사유, 역검증 결과, 예상 영향 포함

**왜:** 오탐/미탐 기록은 사실 관찰 활동이므로 에이전트가 자율적으로 수행하는 것이 효율적. 반면 severity 변경이나 승격/강등은 게이트 작동 방식을 바꾸는 결정적 변화이므로 사람의 판단이 필요.

- **오탐 급증:** 게이트가 정상 글을 자꾸 막음. 규칙 조건이 과잉이거나 YAML 파서 등 하위 계층 문제.
- **배포차단 누적 특정 블로그 집중:** 해당 블로그의 파이프라인 또는 콘텐츠 생성에 문제 있을 가능성.
- **V 카테고리 미탐 발견:** 라이브가 틀렸는데 파일 검사는 통과. V 규칙 강화 필요 신호.

## 5. 에스컬레이션 — 사람 승인 필수 상황

다음 상황은 자동 처리 금지. 사람에게 상황 설명(무엇을, 왜, 어떤 범위, 대안은 무엇인지) + 승인 요청 후 진행.

1. **스케줄러/데몬 재시작:** launchd 재등록, scheduler.py 재기동, 프로세스 PID 변경.
2. **대량 수정:** 10건 이상 포스트 동시 수정, DB UPDATE/DELETE, 배치 스크립트(--dry-run 제외 실실행).
3. **인프라/도메인 변경:** Cloudflare 설정 변경, 도메인 매핑 변경, wrangler deploy 대상 변경, R2 버킷 변경, Workers/Pages 설정 변경.
4. **롤백:** 이전 버전(tag checkout, wrangler 버전 롤백, DB 복원, 파일 복원).
5. **규칙 CRITICAL 승격/삭제:** 기존 규칙의 severity 변경(특히 WARNING→CRITICAL, CRITICAL→삭제).
6. **게이트 우회:** preflight 차단 상태에서 배포 진행.
7. **데이터 손실 가능 작업:** `content.db` 등 발행 기록 DB 변경, 포스트 파일 삭제, 백업 없는 수정.

에스컬레이션 시 포함할 정보:
- 무엇: 어떤 작업인지
- 왜: 왜 필요한지 (문제 증상/배경)
- 범위: 몇 건/어느 블로그/어느 파일
- 대안: 다른 방법이 있는지
- 위험: 이 작업을 안 했을 때의 위험 vs 했을 때의 위험
- 파일럿 여부: 파일럿 검증했는지
