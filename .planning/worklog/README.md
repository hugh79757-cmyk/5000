# Worklog (파괴적 작업 수행 기록)

> 룰: AGENTS.md "파괴적 작업 수행 규칙" 참조. 커밋 또는 파괴적 작업 → worklog 필수.
> 형식: `WL-<YYYYMMDD>-<주제>.md` (예: `WL-20260806-content-db-recovery.md`)

## 양식 (파괴적 작업 포함 작업 단위마다 1개)

```markdown
# WL-YYYYMMDD-주제

> 날짜: YYYY-MM-DD / 연관: PR/커밋 해시 / 상태: 진행중 | 완료 | 보류

## 파괴적 작업 목록
| 시각 | 작업 | 명령/스크립트 | 사전카운트 | 백업 | 사후대조 | 보존확인 |
|------|------|--------------|-----------|------|---------|----------|
| 20:15 | run_sync 재삽입 | python -c "run_sync()" | 42,256→57,770 | bak_20260806_202605 | 15,514 추가 | source='' 36행 유지 |

## 4단계 프로토콜 이행
1. 사전 카운트: ...
2. 되돌림 수단: ...
3. 실행: ...
4. 사후 대조: ...

## 결과 / 보존 대상 확인
- source='' 실발행 행수 before/after: 36 → 36 (유지)

## 잔존 위험
- ...
```

## 예시 (2026-08-06 content.db 사고)

| 시각 | 작업 | 사전카운트 | 백업 | 사후대조 |
|------|------|-----------|------|----------|
| 20:15 | run_sync() — 중복 15,514행 재삽입 (STRUCT-11, non-unique 인덱스) | 42,256행 | 없음(사고) | 57,770행 |
| 20:31 | 오염 증거본 보존 | 57,770행 | content.db.EVIDENCE_polluted_20260806 | 동일 해시 |
| (보류) | 복구: 중복 정리 + UNIQUE 마이그레이션 | 삭제 예정 미확정 | 스케줄러 정지 후 | 미실행 |

상세: `.planning/phase-60-publish-investigation-and-hardening/RECOVERY-content-db-20260806.md`

## 규칙 요약

- 파괴적 작업 전: 사전 카운트 출력 → 사용자 확인(대량 삭제·프로덕션 DB만) → 백업 확보.
- 파괴적 작업 후: `logs/destructive_YYYY-MM-DD.log`에 1줄 append + 이 worklog 1개.
- 민감정보(토큰/비밀번호)는 로그·worklog에 기록 금지 (마스킹).
