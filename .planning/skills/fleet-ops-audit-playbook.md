## 패턴 1: 대량 fail 진위 판별 — (a) 실제결함 / (b) 검사기 오판 / (c) 혼재 분해

### 언제 쓰나
- 헬스체크가 블록 전체(예: 85개 블로그 중 81개, active 23개 중 22개)에서 한꺼번에 fail로 떨어질 때.
- fail 비율이 80%를 넘으면 "전 블록이 고장"보다 "검사기/판정 기준이 블록 전체와 안 맞음"이 먼저다.
- fail을 코드로 즉시 고치기 전에, 대표 사례 2~4개를 라이브로 직접 검증해 원인을 분해한다.

### 절차
1. **fail 집계**: 최신 check_results에서 상태 분포 확인 (fail 수 / 전체 수).
2. **대표 샘플 실측**: fail 블로그 중 2~4곳의 라이브 대상을 직접 조회(HTTP GET)해 검사 대상이 실제로 존재하는지 확인.
3. **판정 분해**:
   - (a) 실제결함 — 검사 대상이 실존하지 않음 (404, 없는 meta, 빈 값).
   - (b) 검사기 오판 — 검사 대상은 실존하나 파서/판정 기준이 실제 형식을 못 읽음.
   - (c) 혼재 — 일부는 실결함, 일부는 오판. 각각 집계해 분리.
4. **(b)면 파서 보정 후 재실행**: fail 수가 실제 결함 수로 수렴하는지 확인. 수렴하지 않으면 다시 분해.
5. **실결함만 이슈 등록**: known_issues에 (a)건만 등록하고, 오판이었던 항목은 이슈로 남기지 않는다.

### 실증 사례 (Phase 60)
| 검사 | 초기 fail | 분해 결과 | 판정 | 후속 |
|------|-----------|-----------|------|------|
| M03 크로스링크 | 740건(beauty) + 677건(pet) = 1,417건 | 오판 1,344건 + 실제 73건 (4개 블로그) | (c) 혼재 | CROSS_GRAPH 인접판정으로 교체 → 실제 73건만 남음 (오판 98% 제거, 커밋 0bf9f922b) |
| render_health og:image | active 23개 중 22개 fail | **오판 22개** — 테마(Blowfish/PaperMod)는 홈페이지가 아닌 포스트 페이지에서 og:image 발행, Blogger는 속성 역순, minified HTML은 unquoted href | (b) 오판 | 파서 보정(포스트 샘플 검사 + 역순/unquoted 지원) → 23/23 pass (커밋 9bec64711) |

### 재사용 체크리스트
- [ ] fail이 블록의 80% 이상이면 검사기 기준 의심 먼저.
- [ ] 홈페이지만 검사하는 헬스체크는 포스트 페이지 검사로 전환했는가?
- [ ] 파서가 minified(unquoted) HTML과 속성 역순(예: Blogger `content=... property=og:image`)을 처리하는가?
- [ ] 오판 항목을 이슈로 남기지 않고 실결함만 등록했는가?
- [ ] 파서 보정 후 fail 수가 실결함 수로 수렴했는가?

## 패턴 2: 무력 체크 감지 — 항상 graceful pass = 미작동 의심

### 언제 쓰나
- 특정 check가 모든 블로그에서 100% pass인데, 해당 검사가 "실제로 뭔가를 검사하고 있다"고 신뢰하기 어려운 상황.
- 헬스체크를 신설/개편했거나, DB 스키마가 바뀐 뒤 pass율이 비현실적으로 높아졌을 때.
- "pass 23/23" 같은 결과가 나오면 통과 사실보다 **왜 전부 통과인지**를 의심한다.

### 절차
1. **pass 집계**: check별로 active 전수 실행 후 pass/fail/unknown 분포 확인.
2. **100% pass check 선별**: 전부 pass인 check를 후보로 뽑는다.
3. **쿼리 대상 검증**: 해당 check가 조회하는 테이블/컬럼이 실제 연결된 DB에 존재하는지 확인.
   - `sqlite_master`로 테이블 존재 확인, `PRAGMA table_info`로 컬럼 확인.
   - 존재하지 않으면 `sqlite3.OperationalError` → try/except가 잡아서 graceful pass 반환 → **무력**.
4. **상태값 검증**: 조회하는 status 값이 실제 기록 값과 일치하는지 확인.
   - 예: 체크가 `status='success'`를 기대하는데 실제 값은 `status='published'`면 항상 0건 → pass.
5. **무력 확정**: (3) 또는 (4)가 원인이면 "무력"으로 판정하고, 검사 대상이 실존하는 DB/컬럼/값으로 연결을 보정한다.
6. **이슈 등록**: 보정 전까지 대시보드에 "미작동"으로 노출되도록 known_issues에 등록한다 (조용한 pass 금지).

### 실증 사례 (Phase 60, 커밋 9bec64711)
| check | 관측 | 원인 | 판정 |
|-------|------|------|------|
| M01 (cjk_leak 본문) | pass 23/23 | ops.db에 `publish_log`/`publish_ledger` **테이블 없음** (실제로는 curation.db/content.db 소유) → 매회 OperationalError → graceful pass | 무력 |
| M07 (similar_title) | pass 23/23 | ops.db에 `publish_ledger` **없음** (content.db 소유) → 항상 pass | 무력 |
| M09 (publish_log 무결성) | fail 1건 검출됨 | content.db/curation.db 직접 연결 — 정상 작동 | **작동 중** (무력 아님) |

- 추가 관측: M09가 이전에 `status='success'`를 기대했으나 실제 publish_ledger는 `status='published'` 사용 — 상태값 불일치 패턴도 동일 원인 계열.

### 재사용 체크리스트
- [ ] 100% pass인 check는 조회 테이블이 연결된 DB에 실존하는지 확인했는가?
- [ ] 기대 status 값이 실제 기록 값(예: published vs success)과 일치하는가?
- [ ] `sqlite3.OperationalError`를 조용히 삼키는 try/except가 없는가?
- [ ] 무력으로 판정되면 known_issues에 등록해 대시보드에서 "미작동"이 노출되는가?
- [ ] 보정 후 active 전수 재실행해 pass/fail이 실제로 갈리는지 확인했는가?

## 패턴 3: 알림 분류 원칙 — 정상 차단=요약, 실제 실패=실시간

### 언제 쓰나
- 파이프라인 알림이 하루 수십 건 쏟아져 소음이 되고, 진짜 장애가 묻힐 때.
- 같은 문제가 매일 반복 발행되는데 대부분 "정상 품질 게이트가 차단한 것"일 때.

### 절차
1. **P-코드별 성격 분류**:
   - **정상 품질 게이트 차단** (콘텐츠가 기준 미달이라 막힌 것 = 시스템이 의도대로 동작): 요약으로.
   - **실제 실패/크래시/미분류** (파이프라인 자체가 죽거나, 원인을 못 박는 신종 오류): 실시간으로.
2. **분류 테이블 교정**: notification_classifier에 P-코드→(summary|realtime) 매핑을 명시적으로 둔다.
3. **디바운스**: 동일 (blog_id, problem_id)는 하루 1회로 억제 (notification_debounce 테이블).
4. **일일 요약**: summary 대상은 텔레그램 일일 요약 1건으로 모아 발송 (daily_summary).
5. **모순 점검**: 요약 화면의 건수가 디바운스 적용 전 원건수인지 확인 — 실제 푸시 건수로 표시해야 소음이 정확히 집계된다.
6. **소음 측정**: 개편 전후 실시간 푸시 건수를 비교해 절감률을 기록.

### 실증 사례 (Phase 60 Part 3, 커밋 96aa342d8 / dc99cef64)
- 분류 교정: P07/P08/P09(정상 게이트 차단 계열) → summary, P01/P02(실제 실패) → realtime.
- P09(repeated segments, 정상 차단) → 일일 요약으로 이동, 실시간 푸시 중단.
- P02(no_result, 실제 파이프라인 실패) → 실시간 유지 + 디바운스.
- **소음 절감: ~82%** — 원래 30~50건/일 → 3~9건/일.
- 추가: generate_summary가 디바운스 미적용 원건수를 표시하던 90건 모순을, debounce 테이블 참조로 실제 푸시 건수 산출하여 해결 (dc99cef64).

### 재사용 체크리스트
- [ ] P-코드별 (정상차단 | 실제실패) 분류표가 명시적으로 있는가?
- [ ] 정상 품질게이트 차단은 요약, 실제 실패/크래시/미분류는 실시간인가?
- [ ] 동일 (blog_id, problem_id) 하루 1회 디바운스가 적용되는가?
- [ ] 요약 표시 건수가 디바운스 후 실제 푸시 건수인가 (원건수 표시 금지)?
- [ ] 개편 전후 소음 절감률을 측정해 기록했는가?

## 패턴 4: 순서 게이트 — 감지 → baseline → 리팩토링 → 확장

### 언제 쓰나
- 대규모 리팩토링(예: 계열 통합, 테마 마이그레이션)이나 확장(예: 15→50 블로그)을 앞두고 있을 때.
- "리팩토링이 회귀를 만들었는지"를 나중에 소급 판정해야 할 때.
- 확장이 실패하면 되돌리기 어려울 때.

### 절차
1. **감지(대시보드)를 회귀탐지기로 먼저**: 헬스체크가 전 블록을 자동 검사하는 상태를 먼저 만든다. 회귀를 눈으로 보는 도구가 없으면 리팩토링을 시작하지 않는다.
2. **baseline 태그**: 리팩토링 직전 커밋에 태그를 찍는다 (예: `pre-refactor-baseline`). 이 커밋은 "이후의 모든 변화"의 비교 기준이 된다.
3. **리팩토링**: 태그 이후 커밋들로 진행.
4. **회귀 판정**: 리팩토링 커밋과 baseline 태그 사이의 상태를 대조해 "원래 문제 vs 리팩토링 회귀"를 가른다.
5. **확장 게이트 (준비도 3지표)**: 확장은 아래 세 지표가 모두 녹색일 때만 착수:
   - 표준 준수율 100% (표준 규칙 위반 0)
   - stale(발행 정지) active 블로그 = 0
   - 미해결 known_issue = 0
   - 하나라도 적색이면 확장 금지 — 지표값을 보고하고 보류.
6. **시범 발행**: 게이트 녹색 후 신규 블로그 1곳을 시범 발행하고 전수 체크 pass를 확인한 뒤 확대.

### 실증 사례 (Phase 60)
- **baseline 태그**: `pre-refactor-baseline` = `d85095152` (2026-08-06, "docs(audit): 5000 아키텍처 감사 보고서") — Phase 59 첫 커밋 직전.
- **회귀 판정**: publish_ledger를 baseline 시각과 대조 → 리팩토링 회귀(d) 0건, 원래 문제(a) 7개 + 시도 중단(b) 52개 (PART1-REPORT.md).
- **준비도 3지표 게이트** (Part 6, 커밋 9bec64711): 표준 0.0% (pass 0/85), stale 7, 미해결 21 → **🔴 확장 금지** → 시범 발행(6-3) 미실행.
- **후속 참고**: 대시보드 완성 이후의 롤백 기준은 `post-dashboard-baseline` 태그가 별도 필요 (pre-refactor-baseline은 대시보드 이전 커밋이라 현재 상태 롤백 기준으로 부적합).

### 재사용 체크리스트
- [ ] 리팩토링/확장 착수 전에 전 블록 자동 헬스체크(회귀탐지기)가 있는가?
- [ ] 작업 직전 커밋에 baseline 태그를 찍었는가? (이후 소급 비교 기준)
- [ ] 회귀 판정은 baseline 태그 시각과 데이터를 대조했는가?
