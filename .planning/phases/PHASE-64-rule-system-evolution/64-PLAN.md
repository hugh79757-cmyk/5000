# Phase 64 — 규칙 체계 자기진화 + 운영헌장

## 목표

Phase 62에서 C01~C08, Phase 63에서 C09를 구축했지만 두 가지 구멍이 확인됐다:

1. **반응적 규칙 목록**: 지금 규칙은 "이번 세션에서 걸린 문제"만 담고 있다. 이미지 깨짐, 중복 발행, 제휴 링크 오류, SEO 메타 누락, 날짜 오류 등은 규칙에 없다.
2. **판단 원칙의 구두 전달**: "파괴적 작업은 파일럿부터", "진본 확인 우선" 같은 원칙이 문서로 안 박혀 있어 에이전트가 매번 같은 사고를 낸다.

이 phase는 규칙 몇 개 추가가 아니라 **자기 진화하는 규칙 체계 + 모든 에이전트가 읽는 운영헌장**을 설계한다.

## 범위

- 규칙 카테고리 재구조화 설계 (C/S/L/P/V 5개 카테고리 + 후보 규칙 정의표)
- 대시보드 세분화 표시 설계 (category 컬럼 필요 여부 포함)
- 자기개선 메커니즘 3종 설계 (leak_tracker 집계, 오탐/미탐 피드백, 신규 규칙 등록 절차)
- 운영헌장 `.planning/OPERATIONS-CHARTER.md` 작성

## 비범위

- 실제 INSERT / 코드 수정 / 배포
- 기존 C01~C09 규칙의 삭제·변경
- S/L/P/V 카테고리 규칙의 실제 구현

## Task 1: 규칙 카테고리 재구조화 설계

**산출물:** `.planning/phases/PHASE-64-rule-system-evolution/64-RULE-CATEGORIES.md`

### 1-1. 기존 C01~C09를 5개 카테고리로 매핑

기존 규칙 9종을 새 카테고리로 재배치한다:

| 기존 규칙 | 새 카테고리 | 사유 |
|-----------|-------------|------|
| C01 곡선따옴표 | C (콘텐츠 무결성) | 프론트매터 값 품질 |
| C02 프론트매터 미종료 | C (콘텐츠 무결성) | 프론트매터 구조 무결성 |
| C03 본문 키 유출 | C (콘텐츠 무결성) | 본문 오염 |
| C04 프롬프트 누수 | C (콘텐츠 무결성) | 본문 오염 (생성 아티팩트) |
| C05 draft:true | P (발행 정합) → C로 유지 검토 | 발행 상태 오류 (단, C05는 프론트매터 문제이기도 함) |
| C06 mtime>배포 | P (발행 정합) | 로컬-배포 시각 불일치 |
| C07 죽은 링크 | L (링크 건전성) | 링크 타겟 생존성 |
| C08 라이브 불일치 | V (라이브-파일 일치) | 라이브-로컬 일치 |
| C09 문자열화 | C (콘텐츠 무결성) | 프론트매터 값 품질 |

**논의 포인트:** C05(draft:true)는 발행 정합(P) vs 콘텐츠 무결성(C) 중 어디에 둘지. C05는 "발행되면 안 되는 게 발행됨"이라는 점에서 P 성격이 강하지만, 현재 CRITICAL 배포차단 규칙으로서 프론트매터 검사와 함께 동작하므로 C에 둘 수도 있다. 이 논의는 설계 문서에 명시하고 결정은 유보하거나 사용자 확인.

### 2-2. 카테고리별 집계 표시 설계

대시보드에서 블로그별·카테고리별 매트릭스를 표시한다:

**요약 뷰 (블로그 리스트 페이지):**
```
blog_id          | C | S | L | P | V | 전체
-----------------+---+---+---+---+---+
health-hugo      | 0 | 0 | 1 | 0 | 0 | 1
kitchen-hugo     | 0 | 3 | 0 | 0 | 0 | 3
car-hugo         | 1 | 0 | 0 | 0 | 0 | 1
```

→ "문제 없음"이 아니라 "C 0 / S 3 / L 0 / P 0 / V 0" 식으로 표시.

**드릴다운 뷰 (블로그 클릭 시):**
- 카테고리별 위반 목록: [{rule_id, slug, severity, detail, created_at}, ...]
- 예: S 카테고리 클릭 → "S01 cover 누락 3건: slugA, slugB, slugC"

### 2-3. check_results 스키마 검토

`check_results` 테이블에 `category` 컬럼이 필요한지 확인:

현재 컬럼: id, blog_id, check_name, status, detail, created_at

필요시 추가 컬럼:
- `category` (TEXT: C/S/L/P/V)
- `severity` (TEXT: CRITICAL/MAJOR/WARNING)
- `rule_id` (TEXT: 규칙 식별자)

**설계 결정 포인트:**
- check_results에는 check_name만 있고 rule_id가 없음. 새 설계에서는 check_name → rule_id 매핑 테이블 또는 check_name에 rule_id 포함(예: "c09_str_list_categories")으로 규칙 ID 획득 가능.
- category 컬럼은 체크 함수 등록 시 `@register_check("c09_str_list_categories", category="C")` 형태로 메타데이터 전달하거나, 별도 매핑 테이블(rule_metadata: rule_id, category, severity, description, auto_action)로 관리.

### 2-4. ops_dashboard UI 표시 설계 (개념만)

Flask 대시보드에서:
- 블로그 리스트: 각 블로그 행에 C/S/L/P/V 5개 컬럼 (숫자 또는 아이콘)
- 색상 코드: CRITICAL=빨강, MAJOR=주황, WARNING=노랑, pass=초록
- 정렬/필터: 카테고리별 필터링, severity별 필터링
- 클릭 시 드릴다운: 해당 카테고리 위반 목록

## Task 3: 자기개선 메커니즘 3종 설계

**산출물:** `.planning/phases/PHASE-64-rule-system-evolution/64-SELF-IMPROVEMENT.md`

### 3-1. 메커니즘 (a): leak_tracker 로그 집계 리포트

**현황:** `shared/leak_tracker.py`가 C01/C04 탐지를 3단계((a)생성직후 (b)humanizer후 (c)저장직전)에서 `logs/leak-origin.log`에 기록 중.

**설계:**
- 로그 형식: `[timestamp] stage={stage} rule={rule_id} blog={blog_id} slug={slug} detected={bool}`
- 집계 주기: 일일 배치 (또는 스케줄러 주기)
- 집계 내용:
  - 규칙별 탐지 횟수 (C01: N건, C04: M건, ...)
  - 단계별 누적: (a)생성직후 N건, (b)humanizer후 M건 (humanizer가 C01/C04를 얼마나 고치는지 지표)
  - 블로그별 분포
  - 추이: 전주 대비 증감
- 출력: `logs/leak-origin-report-{YYYY-MM-DD}.json` + 대시보드 표시

**활용:** "C04가 42건 중 38건이 (c)저장직전 단계에서 탐지됨" → humanizer가 C04를 못 고치고 있다는 신호 → humanizer 개선 또는 프롬프트 조정 검토.

### 3-2. 메커니즘 (b): 오탐/미탐 피드백 기록 구조

**배경:** Phase 63에서 "이미지 0개" 오탐이 발생했다. 게이트가 오탐하거나 미탐하면 규칙 조건이 틀렸다는 신호다.

**기록 구조:**

**오탐 (false positive):** 게이트가 막았는데 알고 보니 정상이었던 케이스
- 기록: {timestamp, blog_id, slug, rule_id, severity, gate_decision, user_judgment, reason, action_taken}
- 예: "C09가 문자열화로 탐지했지만 실제로는 정상 list였음 (YAML 파서 버그)" → 규칙 조건 조정 근거

**미탐 (false negative):** 게이트 통과했는데 라이브에서 문제였던 케이스
- 기록: {timestamp, blog_id, slug, rule_id(故로케), live_issue, detection_gap, action_taken}
- 예: "저혈압 글 C09 통과했지만 라이브 og:title 불일치 → V01 규칙 필요" → 신규 규칙 등록 근거

**저장 위치:** `data/rule_feedback.db` (SQLite) 또는 `logs/rule_feedback.jsonl`

**활용 주기:** 월간 검토 또는 피드백 건수 임계 초과 시 검토

### 3-3. 메커니즘 (c): 신규 규칙 등록 절차 (템플릿화)

이번 C01~C09를 만든 절차를 템플릿으로 문서화한다:

**단계 1: 발견**
- 문제 증상, 영향 범위(몇 건/어느 블로그), 심각도 추정
- 기록: `data/rule_feedback.db` 미탐 레코드 또는 수동 발견 리포트

**단계 2: 임시 관찰규칙 등록 (경고만)**
- rule_id 배정 (카테고리 코드 + 다음 번호)
- SEED_STANDARD_RULES에 severity=WARNING으로 추가 (배포차단 아님)
- check_results에 해당 체크 등록 (또는 기존 체크 확장)
- 로그만 쌓고 배포차단은 하지 않음
- 목적: 실제 탐지 건수/오탐률 데이터 수집

**단계 3: 역검증 (전건탐지 + 오탐0)**
- 검증 데이터 구성: 문제가 있는 샘플(전건탐지 확인용) + 정상 샘플(오탐 확인용)
- `scripts/c01_c08_reverse_validation.py` 패턴 준용: 규칙별 체크 함수 + 검증 데이터 JSON
- 기준: 전건탐지 100% + 오탐 0건 (오탐이 0이 아니면 조건 조정 후 재검증)
- 실패 시: 단계 2로 돌아가서 조건 조정, 또는 규칙 폐기

**단계 4: 정식 승격 (배포차단)**
- severity를 WARNING → CRITICAL (또는 MAJOR)로 변경
- preflight_check, hugo_writer 훅, dashboard 체크에 게이트 적용
- 필요 시: 기존 발행분 소급 검사 (batch 스크립트)

**단계 5: 문서화**
- 규칙 정의서(CONTEXT 문서에 추가 또는 규칙 레지스트리 문서)
- 왜 필요한지 1줄 배경 (어떤 사고에서 나왔는지)
- 운영헌장 업데이트 (해당 규칙군을 만든 판단 원칙 반영)

**참고:** Phase 62에서 C01~C08은 이 절차를 완전히 따르지 않고 바로 CRITICAL로 INSERT됨. Phase 63에서 C09는 2단계(임시 관찰)를 건너뛰고 바로 검증했지만, 역검증(script + 샘플 데이터)은 수행함. 이 phase에서는 절차를 명확히 문서화하고, 앞으로 신규 규칙은 단계 2부터 시작하도록 권장 사항으로 명시.

### 4-3. 절대 원칙

**원칙 1: 진본 경로 확인 우선**
- config site_path가 가리키는 경로가 진짜 진본인지 먼저 확인한다.
- 5000/CUAP/ 아래에 죽은 복사본이 남아 있으면 건드리지 않는다. Phase 61에서 5000/CUAP/health-hugo 죽은 복사본을 제거했지만, 다른 블로그도 같은 패턴일 수 있다.
- 체크: `git remote`, `git log --oneline` 최근 커밋, 실제 파일 수정 시각, config 사이트 경로와 일치 여부.

**원칙 2: 파괴적 작업은 백업→파일럿→검증→확대**
- 대량 수정, rm, 전 포스트 재작성, DB 변경은 파괴적 작업.
- 순서: (1) 백업/스냅샷/태그, (2) 1건 파일럿 수정, (3) 파일럿 검증(규칙 통과/빌드 성공/라이브 확인), (4) 방식 확정 후 확대.
- 파일럿 없이 "일괄 스크립트"로 전수 수정하지 않는다. Phase 63에서 이 이유로 배포 누락 우려가 있었다.

**원칙 3: "일괄 스크립트/전수 재작성"은 위험 신호 — 반드시 파일럿 선행**
- "for 루프 돌려서 다 고친다"는 접근은 범위가 클수록 위험.
- 스크립트는 건조 실행(dry-run) 먼저. --dry-run 또는 --check 모드로 실제 변경 없이 결과만 출력.
- 변경 전/후 diff 또는 SHA 비교로 변경 범위 확인.

**원칙 4: 파일 통계만으로 판정 금지 — 라이브 대조 필수**
- "포스트 274건, frontmatter 파싱 100% 성공" ≠ "라이브도 정상".
- 파일 통계는 필요조건일 뿐 충분조건 아님. V 카테고리 규칙(V01~V03)이 이 격차를 메우기 위한 것.
- 가능하면 HTTP HEAD/GET으로 라이브 확인. CDN 지연 시 purge 고려.

**원칙 5: 게이트 우회 금지**
- preflight_check가 blocked=True면 배포하지 않는다. "급하니까" 우회하지 않는다.
- 우회해야 하는 상황이라면 그 이유를 문서화하고 사용자 승인 기록.
- C 카테고리 CRITICAL 규칙(C01/C02/C04/C09 등)은 우회 대상 아님.

**원칙 6: 규칙 변경/추가는 역검증 통과 후에만**
- 신규 규칙은 단계 2(임시 관찰, 경고만) → 단계 3(역검증 전건탐지+오탐0) → 단계 4(승격) 순서로.
- 오탐이 있는 규칙을 CRITICAL 배포차단으로 승격하면 정상 글을 막는 거짓 양성 발생.
- 기존 규칙을 완화/삭제할 때도 역검증으로 "완화해도 진짜 문제를 놓치지 않는지" 확인.

## 4. 최종 구분: 사람 승인 필수 7종 vs 완전 자동 영역

### 4.1 사람 승인이 여전히 필수인 7종

| 번호 | 작업 유형 | 승인이 필요한 이유 | 승인 요청 시 포함 정보 |
|------|-----------|-------------------|------------------------|
| 1 | **스케줄러/데몬 재시작** | launchd 재등록, scheduler.py 재기동, 프로세스 교체 — 발행 스케줄에 즉시 영향 | 재시작 사유, 영향 범위, 대안 |
| 2 | **대량 수정 (10건 이상)** | 잘못된 수정이 수백 건에 동시 반영 위험 | 수정 내용, 대상 범위, 파일럿 결과, 백업 위치 |
| 3 | **인프라/도메인 변경** | Cloudflare 설정, 도메인 매핑, R2 버킷 등 — 전체 블로그 영향 | 변경 내용, 영향 블로그, 롤백 계획 |
| 4 | **롤백** | 이전 버전으로 되돌리기 — 라이브에 직접 영향 | 롤백 사유, 대상, 현재 상태 백업, 영향 범위 |
| 5 | **규칙 CRITICAL 승격/삭제** | 게이트 작동 방식 변경 — 정상 글 차단 또는 문제 누락 가능 | 규칙 ID, 변경 내용, 역검증 결과, 예상 영향 |
| 6 | **게이트 우회** | preflight blocked=True 상태에서 배포 진행 — 오염된 콘텐츠 라이브 배포 위험 | 우회 사유, 차단 규칙, 대안, 위험 수용 의사 |
| 7 | **데이터 손실 가능 작업** | content.db 등 발행 기록 DB 변경, 포스트 파일 삭제 — 복구 불가 가능성 | 작업 내용, 대상, 백업 여부, 복구 계획 |

### 4.2 완전 자동으로 도는 영역

| 영역 | 내용 | 자동화의 근거 |
|------|------|---------------|
| **규칙 오탐/미탐 기록** | 에이전트가 게이트 판단 중 발견 시 `logs/rule_feedback.jsonl`에 자동 기록 | 사실 관찰 활동, 사람의 판단이 필요하지 않음 |
| **관찰단계 규칙 등록 (WARNING)** | 신규 규칙을 WARNING severity로 SEED_STANDARD_RULES에 추가 | 배포차단 없음, 데이터 수집 목적 |
| **체크리스트 항목 1~5 수행** | 진본경로 확인, 백업, 파일럿, 라이브 대조, 게이트 확인 — 에이전트가 자율적으로 수행 | 절차적 확인, 사람의 판단이 필요한 결정 아님 |
| **단일 블로그 일반 배포** | dispatcher.py를 통한 단일 블로그 글 생성+발행+배포 | 임계 이하 작업, preflight 게이트 통과가 선행 조건 |
| **프리플라이트 체크리스트 출력** | 작업 전 체크리스트 항목을 출력·확인하는 행위 자체 | 프로세스 준수, 에이전트 자율 수행 |
