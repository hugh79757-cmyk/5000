# Phase 64 — Task 6: 작업 유형별 프리플라이트 체크리스트

> **목적:** 에이전트가 작업 시작 시 헌장 전체를 읽지 않아도, 작업 유형별로 반드시 확인해야 할 체크리스트를 프롬프트 템플릿에 삽입하여 강제하는 것.
>
> **위치:** `.planning/phases/PHASE-64-rule-system-evolution/64-PREFLIGHT-CHECKLISTS.md`
>
> **성격:** 이 체크리스트는 "왜"를 설명하는 운영헌장과 달리 "매번 강제되는 행동"이다. 헌장은 배경, 체크리스트는 실행 게이트.

---

## 1. 설계 원칙

### 1.1 왜 체크리스트가 필요한가

운영헌장(`.planning/OPERATIONS-CHARTER.md`)은 219줄이다. 에이전트가 작업 전 매번 전체를 읽는 것은 비효율적이고, 실제로 읽었는지 확인하기도 어렵다. 대신 **작업 유형에 맞는 짧은 체크리스트(5~7개 항목)를 프롬프트 템플릿에 삽입**하면:

1. 에이전트가 작업 직전에 반드시 출력·확인하게 된다.
2. 체크리스트 항목 하나하나가 구체적 행동 지시이므로 " 읽었다"가 아니라 "체크했다"로 확인 가능하다.
3. 91건 사고와 같은 패턴이 발생했을 때, "어느 체크 항목에서 잡았을까"를 역추적할 수 있다.

### 1.2 체크리스트 구성

각 체크리스트는 다음 6개 표준 항목으로 구성된다:

| 번호 | 항목 | 내용 |
|------|------|------|
| 1 | 진본경로 확인 | 수정 대상 파일/DB가 config에 등록된 진본 경로인지 확인 |
| 2 | git tag 백업 | 작업 전 현재 상태에 git tag 또는 백업 확보 |
| 3 | 파일럿 1건 선행 | 대량 작업 시 1건만 먼저 적용 → 검증 |
| 4 | 라이브 대조 | 가능하면 HTTP로 라이브 확인 (로컬 파일 ≠ 라이브) |
| 5 | 게이트 통과 | preflight_check 등 자동 게이트 통과 확인 |
| 6 | 사람 승인 필요 여부 | 이 작업은 사람 승인이 필요한지 판단하고, 필요하면 요청 |

작업 유형에 따라 일부 항목은 "해당 없음(N/A)"일 수 있다. N/A인 경우 그 이유를 간략히 기록한다.

```
   - 파일럿 대상: [파일/레코드 식별자]

□ 6. 사람 승인 필요 여부
   - 이 작업은 10건 이상 동시 수정이므로 **사람 승인이 필요**하다.
   - 승인 요청 내용: [무엇을/왜/어느 범위/대안/위험]

※ 체크리스트를 모두 확인하지 않고 작업을 시작하면 안 된다.
※ dry-run 먼저: 스크립트는 --dry-run/--check 모드로 실제 변경 없이 결과 출력 후 확인
```

### 2.3 규칙 변경 (Rule Change)

**정의:** 신규 규칙 추가, 기존 규칙의 severity 변경, 규칙 조건 수정, 규칙 삭제.

**적용 예:** SEED_STANDARD_RULES INSERT/UPDATE, 체크 함수 추가/수정, severity WARNING→CRITICAL 변경

```
╔══════════════════════════════════════════════════════════════════╗
║  프리플라이트 체크리스트 — 규칙 변경                                  ║
╚══════════════════════════════════════════════════════════════════╝

작업 전 반드시 아래 항목을 출력하고 확인한다.

□ 1. 진본경로 확인
   - 수정 대상 파일이 프로젝트의 진본 위치인가?
   - ops_dashboard/db.py, content_integrity.py 등 규칙 관련 파일의 실제 경로 확인.
   - 확인 결과: [파일 경로] → [진본/불일치]

□ 2. git tag 백업
   - 규칙 변경 전 현재 db.py/체크 함수의 상태를 git tag로 남겼는가?
   - 태그명: [태그명 또는 "미태그"]

□ 3. 파일럿 1건 선행
   - 신규 규칙: 단계 2(관찰규칙, WARNING)으로 먼저 등록했는가?
   - 기존 규칙 수정: 수정 후 역검증 스크립트 실행했는가?
   - 역검증 결과: [전건탐지 100% / 오탐 0건 / 실패 — 사유]

□ 4. 라이브 대조
   - 규칙이 라이브 감지를 포함하는 경우(V 카테고리 등): 라이브 비교 API/HTTP 확인 가능한가?
   - 확인 가능 여부: [가능/불가능 — 사유]

□ 5. 게이트 통과
   - 규칙 변경 자체가 preflight 게이트를 통과해야 하는 것은 아님 (규칙 정의는 게이트 이전)
   - 단, 변경된 규칙을 적용한 후 preflight_check가 의도대로 동작하는지 확인했는가?
   - 확인 결과: [정상 동작/이상 — 사유]

□ 6. 사람 승인 필요 여부
   - **규칙의 severity 변경(WARNING↔CRITICAL↔MAJOR) 또는 승격/강등은 사람 승인 필수.**
   - 신규 규칙 추가(관찰단계, WARNING): 사람 승인 불필요 (자동 등록 가능)
   - 기존 규칙 완화/강화: 역검증 통과 + 사람 승인 필요
   - 규칙 삭제: 사람 승인 필수
   - 승인 필요 여부: [불필요/필요 — 변경 내용 + 역검증 결과 첨부]


※ 오탐/미탐 기록은 에이전트가 자동 수행 가능 (logs/rule_feedback.jsonl)
※ 오탐/미탐 기록과 달리,severity 변경이나 승격/강등은 사람의 명시적 승인 필요
※ 역검증 없이 CRITICAL로 승격하면 정상 글을 막는 거짓 양성 발생 → 신뢰 하락
```

### 2.4 롤백 (Rollback)

**정의:** 이전 상태로 되돌리는 작업. git checkout, wrangler 버전 롤백, DB 복원, 파일 복원 등.

**적용 예:** 잘못된 배포 revert, DB 테이블 과거 스냅샷 복원, 파일 삭제 취소

```
╔══════════════════════════════════════════════════════════════════╗
║  프리플라이트 체크리스트 — 롤백                                      ║
╚══════════════════════════════════════════════════════════════════╝

작업 전 반드시 아래 항목을 출력하고 확인한다.

□ 1. 진본경로 확인
   - 롤백 대상 경로/DB가 실제 영향을 미치는 진본 위치인가?
   - 죽은 복사본이나 테스트 환경를 롤백하는 것은 아닌가?
   - 확인 결과: [대상] → [진본/죽은복사본/불일치]

□ 2. git tag 백업
   - 롤백 전 현재 상태(롤백 대상)를 git tag로 남겼는가?
   - 롤백은 "되돌리는" 작업이지만, 롤백 자체도 변경이므로 백업 필요.
   - 태그명: [태그명 또는 "미태그 — 사유:"]

□ 3. 파일럿 1건 선행
   - 롤백의 영향을 받는 범위를 1건(예: 1개 블로그/1개 테이블)으로 좁혀 테스트했는가?
   - 테스트 결과: [롤백 후 상태 확인 결과]

□ 4. 라이브 대조
   - 롤백 후 라이브 상태를 HTTP로 확인했는가?
   - CDN 캐시로 인해 롤백 결과가 즉시 반영되지 않을 수 있음. 확인 시 지연 고려.
   - 확인 URL: [라이브 URL]
   - 확인 결과: [롤백 반영됨/반영 안 됨 — CDN 지연 의심/확인 불가]

□ 5. 게이트 통과
   - 롤백 후 preflight_check가 통과하는가? (롤백으로 인해 새로운 위반 발생하지 않았는지)
   - preflight 결과: [blocked=True/False]

□ 6. 사람 승인 필요 여부
   - **롤백은 사람 승인이 필수다.**
   - 롤백 사유, 영향 범위, 대안(롤백 대신 수정 등)을 문서화하여 승인 요청.
   - 승인 여부: [대기 중/승인됨/거부됨]


※ 롤백은 "이미 배포된 것"을 되돌리는 작업이므로, 라이브에 실제 영향을 미침.
※ 롤백 전 현재 상태를 반드시 백업(tag/스냅샷). 롤백 실패 시 원상복구 수단 확보.
※ content.db 등 발행 기록 DB의 롤백은 실발행 기록 유실 가능성 → 특히 주의.
```

### 2.5 스케줄러 재개 (Scheduler Resume)

**적용 예:** launchd plist 재등록, scheduler.py 프로세스 재시작, PID 변경, 스케줄 간격 변경

```
╔══════════════════════════════════════════════════════════════════╗
```

```
[해당 작업 유형 체크리스트 전문 삽입]

각 항목 확인 결과를 작업 로그에 기록한다.
```

## 4. 체크리스트 항목 간 의존성

일부 항목은 다른 항목에 선행한다:

```
진본경로 확인(1) → 파일럿 1건 선행(3) → 게이트 통과(5) → 라이브 대조(4)
                                                          ↑
                                          (배포/수정 후 최종 확인)

git tag 백업(2)은 항상 첫 번째 또는 작업 직전에 수행.
사람 승인 필요 여부(6)는 다른 항목 확인 후 최종 판단.
```

## 5. 체크리스트 예외 처리

### 5.1 N/A 항목 처리

작업 유형에 따라 일부 항목이 적용되지 않는 경우:

- 체크리스트에 "N/A"라고 표시하고 **그 이유를 한 줄로 기록**한다.
- 예: 배포 작업의 파일럿 항목 → "N/A — 배포는 파일럿 개념 대신 테스트 블로그 선행 배포로 대체"

### 5.2 체크리스트 우회

- 체크리스트를 우회해야 하는 상황은 **극히 예외적**이어야 한다.
- 우회 시: 우회 사유 + 위험 수용 의사를 문서화하여 사람 승인 기록.
- "급하니까" "이미 알고 있으니까"라는 이유로 체크리스트 항목을 건너뛰지 않는다.
