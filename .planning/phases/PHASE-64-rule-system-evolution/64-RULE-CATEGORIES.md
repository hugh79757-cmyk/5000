# Phase 64 — 규칙 카테고리 재구조화 설계

## 1. 기존 C01~C09 → 5개 카테고리 매핑

| 기존 규칙 ID | 현재 이름 | 새 카테고리 | 재분류 사유 | 비고 |
|--------------|-----------|-------------|-------------|------|
| C01 | 프론트매터 곡선따옴표 | **C** (콘텐츠 무결성) | 프론트매터 값 품질 — YAML 파싱 에러 유발 | 유지 |
| C02 | 프론트매터 미종료 | **C** (콘텐츠 무결성) | 프론트매터 구조 무결성 — Hugo 빌드 실패 직접 원인 | 유지 |
| C03 | 본문 프론트매터 키 유출 | **C** (콘텐츠 무결성) | 본문 오염 (프론트매터 값이 본문으로 새어 나옴) | 유지 |
| C04 | LLM 프롬프트/사고문 누수 | **C** (콘텐츠 무결성) | 본문 오염 (생성 아티팩트) | 유지 |
| C05 | draft:true 발행 대상 | **P** (발행 정합) | "발행되면 안 되는 글이 발행됨" — 발행 정합 문제. 프론트매터 검사 지점에서의 탐지는 유지하되 카테고리만 P로 이동 | 결정 반영: C→P 이동, severity CRITICAL 유지 |
| C06 | 로컬 mtime > 배포 시각 | **P** (발행 정합) | 로컬-배포 시각 불일치 — 발행 정합 문제 | 이동 완료 |
| C07 | 죽은 크로스셀 링크 | **L** (링크 건전성) | 링크 타겟 생존성 | 유지, L로 재분류 |
| C08 | 라이브-파일 불일치 | **V** (라이브-파일 일치) | 라이브-로컬 일치 문제 | placeholder 유지, V로 재분류 |
| C09 | categories/tags 문자열화 | **C** (콘텐츠 무결성) | 프론트매터 값 품질 — Hugo range 실패 | 유지 |

**결정 반영 — C05(draft:true)의 카테고리 이동:**
- **결정:** C05는 P(발행 정합) 카테고리로 이동한다.
- **사유:** "발행되면 안 되는 글이 발행됨"은 콘텐츠 자체의 결함(C)보다 발행 프로세스 정합(P) 문제. draft:true 글을 배포하면 독자에게 미완성 콘텐츠가 노출되는 발행 사고.
- **유지 사항:** C05는 CRITICAL 배포차단 severity를 유지하며, 프론트매터 검사 지점에서의 탐지 로직은 그대로 동작한다. 범주만 P로 재분류.
- **표시:** 규칙 레퍼런스에서는 "P05"로 표기하되, 기존 C05와의 이력 연결을 위해 메타데이터에 `legacy_id: "C05"` 기록. (실제 코드 변경은 별도 승인 단계에서 처리)

## 2. 카테고리별 정의

### C — 콘텐츠 무결성 (Content Integrity)

**정의:** 콘텐츠 본문과 프론트매터의 내부적 무결성. LLM 생성 과정에서 유입된 오염, 잘못된 직렬화, 구조적 결함이 없는 상태.

**현재 커버:** C01, C02, C03, C04, C09 (C05 검토 중)

**왜 이 카테고리가 필요한가:** LLM이 생성한 콘텐츠는 사람 손을 거치지 않으면 프론트매터 값 오류(곡선따옴표, 문자열화), 본문 오염(프롬프트 누수, 키 유출), 구조 결함(미종료)이 자연스럽게 발생한다. 배포 전에 이 결함이 걸러지느냐가 콘텐츠의 기본 사용 가능 여부를 결정한다.

**배경 사고:**
- C01/C02: 여러 블로그에서 YAML 파싱 실패로 Hugo 빌드 오류 발생 (Phase 61 이전 반복)
- C04: 본문에서 "생각해보자""We need to write" 등 LLM 사고과정이 그대로 노출 — 독자 신뢰도 훼손
- C09: categories/tags 문자열화로 Hugo `range .Params.categories` 실패 → 해당 섹션 렌더링 누락 (Phase 63: laptop 16건 + health 11건)

### S — 구조/SEO (Structure & SEO)

**정의:** 콘텐츠가 검색엔진과 독자 경험에 적합한 구조를 갖추고 있는지. 커버 이미지, 헤딩 체계, 메타 설명, 내부 링크, 구조화 데이터 등.

**현재 커버:** 없음 (미구현)

**왜 이 카테고리가 필요한가:** 현재 규칙은 "콘텐츠가 깨졌는가"만 본다. "콘텐츠가 검색과 독자 경험에 적합한가"는 보지 않는다. 이 때문에 Phase 63에서 "이미지 0개" 판정 시 파일 통계만으로는 실제 이미지 존재 여부를 판정 못 하는 맹점이 드러났다. S 카테고리는 이 격차를 메운다.

**미구현 관찰대상 (후보 규칙):**

| rule_id | 대상 | 판정 로직 (개요) | severity | 자동조치 | 배경/필요성 |
|---------|------|----------------|----------|----------|-------------|
| S01 | frontmatter | featureimage/cover가 없거나 빈 값 — 사이트 기본값만 의존 | **WARNING** | 경고 + 로그 | 커버 이미지 누락=클릭률/SEO 저하. 단, Nullable 여부와 기본값 정책 확인 필요. **결정 반영: severity MAJOR→WARNING. 커버 이미지 누락은 배포 차단 수준이 아닌 권장 수준으로 판정.** |
| S02 | body | H2 섹션 수 < 최소 기준 (예: 2개 미만) | MAJOR | 경고 + 로그 | 부실 콘텐츠 지표. Phase 54 품질 체크리스트 H2 cap과 중복 검토 필요 |
| S03 | frontmatter | description이 50자 미만이거나 기본 placeholder 패턴과 일치 | MAJOR | 경고 | 메타 설명 부실=검색 노출 품질 저하. Phase 63 저혈압 글 og:description 불일치 조사와 연결 |
| S04 | body | 내부 링크(다른 자사 블로그 post 링크) 0개 | WARNING | **권장(WARNING)** | Phase 25 크로스링크 퍼널 목적 저해. **결정 반영: 강제수준=권장(WARNING). 모든 글에 내부링크를 강제하지 않고, 있으면 좋은 권장 수준으로 운영. WARNINGseverity이지만 자동조치 없음(로그 기록만).** |
| S05 | body | JSON-LD(schema.org) 스크립트 누락 | MAJOR | 경고 | SEO 풍부한 결과 기회 상실. hugo_writer.py `_build_schema_json` 출력 확인 |

### L — 링크 건전성 (Link Health)

**정의:** 콘텐츠 내 모든 링크(크로스셀, 제휴, 외부, 이미지)의 타겟이 유효하고 정책에 부합하는지.

**현재 커버:** C07 (크로스셀 링크만 — 정보핫 포스트 대상)

**왜 이 카테고리가 필요한가:** C07은 정보핫 크로스셀 링크만 본다. 제휴 링크(coupang 등), 외부 링크, 이미지 URL의 생존성은 검사하지 않는다. 깨진 제휴 링크는 수익 기회 상실 + 사용자 신뢰 저하로 직결된다.

**미구현 관찰대상 (후보 규칙):**

| rule_id | 대상 | 판정 로직 (개요) | severity | 자동조치 | 배경/필요성 |
|---------|------|----------------|----------|----------|-------------|
| L01 | body (제휴/affiliate 링크) | coupang/제휴 링크 href가 올바른 도메인이 아니거나 잘못된 파라미터 | CRITICAL | 배포차단 + 로그 | 잘못된 제휴 링크=수익 기회 상실 + 사용자 신뢰 저하. C07의 확장 |
| L02 | body (이미지 URL) | 이미지 URL이 HTTP 응답 없음/404 (C07이 링크면, L02는 이미지면) | MAJOR | 경고 + 로그 | 이미지 깨짐=콘텐츠 품질 저하. Phase 63 "이미지 0개" 오탐과 연결 — 실제 HTTP 확인 필요 |
| L03 | body (외부 링크) | 제휴/광고 목적 외부 링크에 rel="nofollow" 미설정 | WARNING | 경고 | 제휴 링크 정책 준수. nofollow 누락=SEO 정책 위반 가능성 |

### P — 발행 정합 (Publishing Integrity)

**정의:** 콘텐츠가 의도대로 발행되었는지. 발행 상태, 발행 시각, 중복, 메타데이터 일관성을 포함.

**현재 커버:** C05(검토중), C06(mtime)

**왜 이 카테고리가 필요한가:** "콘텐츠가 괜찮아 보여도 발행 과정에서 문제가 생길 수 있다." draft 글이 발행되거나, 배포 누락으로 로컬만 수정되고 라이브에 반영 안 되거나, 날짜가 잘못되거나, 중복 발행되는 문제는 C 범주(콘텐츠 자체)와 다른 차원의 문제다.

**미구현 관찰대상 (후보 규칙):**

| rule_id | 대상 | 판정 로직 (개요) | severity | 자동조치 | 배경/필요성 |
|---------|------|----------------|----------|----------|-------------|
| P01 | frontmatter | date가 미래 날짜( publication 지연 과다) 또는 1년 이상 과거(날짜 오류 의심) | MAJOR | 배포차단 + 로그 | 날짜 오류=콘텐츠 신뢰도 저하. 발행 스케줄 이상 징후 |
| P02 | frontmatter+ledger | 동일 blog_id+slug로 이미 published_url이 Ledger에 존재 (중복 발행) | CRITICAL | 배포차단 + 로그 | 중복 발행=사용자 혼란 + SEO 페널티 가능. Phase 49 크로스링크 9840건 수정 시 slug 문제로 발행 혼란 경험 |
| P03 | frontmatter | categories 값이 사이트 허용 카테고리 정책 목록에 없음 | MAJOR | 경고 + 로그 | 카테고리 정책 위반=사이트 일관성 저하. 허용 목록 관리 필요 |
| P04 | frontmatter | slug가 날짜 접두어 없거나 허용되지 않는 형식 (예: date-prefixed 기대 사이트에서 비접두어 slug) | MAJOR | 경고 | URL 체계 일관성. Phase 49에서 slug 불일치로 9840개 링크 수정한 사고와 직접 연결 |

### V — 라이브-파일 일치 (Version Verification)

**정의:** 로컬 파일이 정상이라도 라이브 사이트가 실제로 그 파일을 서빙하고 있는지. 배포 누락, CDN 캐시, 서드파티 주입 등으로 불일치가 발생할 수 있다.

**현재 커버:** C08 (placeholder, 미구현)

**왜 이 카테고리가 필요한가:** Phase 63에서 결정적 발견: health 저혈압 글은 로컬 파일이 정상(C01/C02/C09 통과)이지만, 라이브 og:title이 "건강기능식품 추천 가이드"로 불일치하고 본문에도 곡선따옴표가 존재했다. "파일 검사 통과 = 라이브 정상"이라는 가정이 깨졌다. V 카테고리는 이 격차를 메운다.

**미구현 관찰대상 (후보 규칙):**

| rule_id | 대상 | 판정 로직 (개요) | severity | 자동조치 | 배경/필요성 |
|---------|------|----------------|----------|----------|-------------|
| V01 | live+file | 라이브 `<title>`/og:title과 파일 `title:` 불일치 | CRITICAL | 배포차단 + 로그 | Phase 63 저혈압 글 발견: 파일 title="저혈압 증상..." / 라이브 og:title="건강기능식품 추천 가이드" |
| V02 | live+file | 라이브 og:description과 파일 description 불일치 (또는 프론트매터 키 유출) | MAJOR | 경고 + 로그 | Phase 63 저혈압 글 og:description에 프론트매터 키가 누출된 형태로 서빙됨 |
| V03 | live+file | 라이브에 파일이 없는 광고 스크립트/추가 콘텐츠가 주입됨 (서드파티 주입 탐지) | MAJOR | 경고 + 로그 | 무고한 광고 주입=사용자 경험 훼손 + 의도치 않은 수익 유출 가능성 |

## 3. severity별 자동조치 정의

| severity | 자동조치 | preflight 게이트 | 대시보드 표시 | Telegram 알림 |
|----------|----------|-----------------|--------------|---------------|
| **CRITICAL** | 배포차단 (blocked=True) | 차단 | 🔴 fail (빨강) | 발송 (문제 등록) |
| **MAJOR** | 규칙별 결정 (차단 또는 경고) | 차단 또는 경고 | 🟠 fail/warn (주황) | 필요 시 발송 |
| **WARNING** | 경고 + 로그만, 배포차단 안 함 | 통과 (경고 기록) | 🟡 warn (노랑) | 발신 안 함 (노이즈 방지) |

**결정 기준:** CRITICAL은 "이 결함이 있으면 배포했을 때 독자에게 직접 피해가 발생하는" 규칙. MAJOR는 "콘텐츠 품질/정책에 위반되지만 즉시 배포차단 수준은 아닌" 규칙 — 단, P02(중복 발행)처럼 독자에 직접 영향 있으면 CRITICAL 가능.

## 4. rule_id 네이밍 규칙 및 네임스페이스 분리

### 4.1 규칙 식별자 (Rule ID)

- 형식: `{카테고리코드 1자}{2자리 숫자}` (예: `C10`, `S01`, `L01`, `P01`, `V01`)
- 카테고리 코드: `C`(콘텐츠 무결성), `S`(구조/SEO), `L`(링크 건전성), `P`(발행 정합), `V`(라이브-파일 일치)
- 숫자: 카테고리 내에서만 순차 부여. 기존 C01~C09는 역사적 이유로 유지하고, 새 규칙만 C10부터 시작.
- 접두어 규칙: 모든 규칙 ID는 `RULE-` 접두어를 붙여 전체 문서/로그에서 네임스페이스 분리:
  - 예: `RULE-C01`, `RULE-S01`, `RULE-L01`, `RULE-P05`(구 C05), `RULE-V01`

### 4.2 문제 인스턴스 식별자 (Issue ID)

- 형식: `ISSUE-{4자리 숫자}` (예: `ISSUE-0001`, `ISSUE-0042`)
- 용도: 규칙 위반이 발생한 **구체적 인스턴스**를 추적할 때 사용
- 예시:
  - "health-hugo 저혈압 글 C09 위반" → 문제 인스턴스: `ISSUE-0001`
  - "kitchen-hugo S01 cover 누락 3건" → 문제 인스턴스: `ISSUE-0002`
- 규칙 vs 문제 구분:
  - `RULE-C09`: "문자열화"라는 **규칙 자체** (무엇을 검사하는지)
  - `ISSUE-0001`: "health-hugo 저혈압 글"이라는 **구체적 위반 사례** (언제/어디서 발생했는지)

### 4.3 namespace 충돌 해결 (확정)

- 기존 PROBLEM_REGISTRY(Phase 58)의 `P01`~`P24`(문제 ID)와 새 P 카테고리 규칙 코드 충돌 해소:
  - **규칙(rule_id):** `P01`, `P02` 등 사용 가능. 문헌에서는 `RULE-P01` 형태로 prefix 표기.
  - **문제(problem_id):** 기존 `P01`~`P24`는 그대로 유지하되, 신규 문제 등록 시 `ISSUE-####` 형식 사용. 기존 PROBLEM_REGISTRY 항목은 `ISSUE-`로 마이그레이션하지 않고 레거시 문서로 남김.
  - **코드상 구분:** 규칙 검사 결과는 `rule_id` 필드에, 문제 등록은 `problem_id` 필드에 저장하여 컬럼 수준에서 분리.

## 6. 설계 결정 필요 사항 (사용자 확인용)

1. **C05 카테고리:** C 유지 vs P 이동. 권장: P 이동 (배포차단 severity 유지).
2. **P namespace 충돌:** 규칙 rule_id(`P01`) vs 문제 problem_id(`P01`) 충돌 해결 방안. 권장: 문제 ID에 `PRB-` prefix 부여.
3. **C06 현재 위치:** 현재 C 카테고리에 있지만 P로 이동하는 것이 자연스러움. 이 phase에서 재분류할지와 실제 코드 태그 변경 여부는 분리 (문서는 P로 표기, 코드 태그는 후속 단계).
4. **S01 cover 누락 severity:** 모든 글에 featureimage 필수인지, Nullable 허용인지에 따라 severity 달라짐. 현재는 "기본 썸네일 있으면 통과" 처리 중.
5. **S04 내부링크 강제 수준:** 모든 글에 내부링크 필수 vs 권장(warning). Phase 25 퍼널 목적과 충돌 여부 확인.
