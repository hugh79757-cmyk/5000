    **The adapter must:**
    - **Preserve the existing entry function** — do NOT rename or delete `run()`, `run(cfg=None)`. The dispatcher `inspect.signature` bridge (L463-465) still works because the module still has a callable named `run`; adding a new dict-normalizing wrapper must not remove it.

    - **Delegate, not rewrite** — the adapter calls the existing `run`/generation logic; it must NOT change any generation behavior. It only shapes the return value.
    - If a module already returns a dict from `run(cfg)`, leave it as-is (no adapter needed) — only add adapters where the contract diverges.

    **Implementation approach (least invasive):**
    - Add a single shared helper in `pipelines/etap/_contract.py`: `def _normalize_result(result) -> dict` that converts bool/None/str to the standard dict. Then, in each diverging `{topic}_pipeline.py`, wrap the existing run body's return OR add a `run(cfg)`-compatible adapter that calls the existing logic and normalizes. (NOTE: `_normalize_result` MUST live in `pipelines/etap/_contract.py` — the automated verify imports it from there.)
    - IMPORTANT: because dispatcher calls via `inspect.signature` (checks if 'cfg' in params), an adapter that keeps `run()` (no cfg) continues to be called as `run()`. The normalization must therefore happen INSIDE the existing `run` (wrap its return), not by adding a parallel `run(cfg)` that the dispatcher may not select. Verify the dispatcher selection per-module before choosing the wiring: modules whose run has no 'cfg' param are invoked as `run()`, so normalize inside that function; modules with 'cfg' param invoked as `run(cfg)`, normalize there.
