# 에이전트 운영 오류 대응 프로토콜

**문서 상태:** 운영 표준 초안 1.0  
**대상:** 5000 프로젝트의 대시보드, 발행 파이프라인, 배포·검증·알림 경로를 다루는 에이전트  
**목표:** 대시보드에 나타난 신호를 단순 경고로 소비하지 않고, 증거 기반으로 **분류 → 진단 → 최소 수정 → 검증 → 기록**하는 반복 가능한 운영 절차를 제공한다.

> **핵심 원칙:** Telegram 문구는 알림 채널일 뿐이며 진실 원천이 아니다. 에이전트는 구조화된 오류 이벤트, 실행 로그, 실제 데이터베이스, 설정 파일, 라이브 결과를 교차 검증한 뒤에만 원인을 확정한다.

## 1. 적용 범위와 우선순위

이 프로토콜은 발행 실패뿐 아니라 발행 안전성과 운영 신뢰성에 직접 영향을 주는 신호를 다룬다. 정상 품질 게이트의 차단, 과거 콘텐츠의 개선 권고, 실제 실행 실패를 같은 수준으로 취급하면 알림 소음과 오판이 발생하므로 아래 우선순위를 사용한다.

| 계층 | 대상 | 기본 행동 | 자동 수정 가능 여부 |
|---|---|---|---|
| **실행 장애** | scheduler timeout, source unavailable, deploy failure, result contract 오류 | 즉시 증거 수집 및 원인 분류 | 조건부 가능 |
| **발행 무결성** | duplicate guard, frontmatter schema, post-publish validation, API rate limit | 발행 중단 여부와 재시도 가능성 판단 | 조건부 가능 |
| **운영 관측** | stale data, freshness, image URL, readiness, domain health | 영향도·오탐 여부를 확인하고 작업 큐화 | 대체로 제안만 |
| **검사기 신뢰성** | validation defect, 다수 동시 fail, 모든 항목 pass | 검사기 자체를 진단하고 오탐/미탐 기록 | 코드 수정은 검증 후 가능 |
| **정상 제어 흐름** | quota reached, already running, 정상 품질 게이트 차단 | 알림 억제 또는 요약; 실패로 승격하지 않음 | 수정 금지 |

## 2. 진실 원천과 증거 우선순위

에이전트는 아래 순서로 증거를 수집한다. 상위 증거와 하위 증거가 충돌하면 상위 증거를 우선하고, 충돌 자체를 사건 기록에 남긴다.

| 우선순위 | 증거 | 용도 | 금지된 해석 |
|---:|---|---|---|
| 1 | `publish_error_events` 및 실행별 원시 로그 | 발생 시각, 블로그, 단계, 재시도, 실제 예외 확인 | Telegram 문구만 보고 원인 확정 |
| 2 | 발행 결과 JSON, scheduler 반환값, subprocess 종료 코드 | 성공/실패 계약 및 실패 전파 확인 | 종료 코드 `0`만으로 성공 판정 |
| 3 | 설정 파일·파이프라인 코드·테스트 | 예상 경로와 실제 구현 비교 | 파일명만으로 실행 경로 추정 |
| 4 | 콘텐츠·수집·발행 데이터베이스 | 후보 소진, 중복, 상태값, 데이터 품질 검증 | 행 수만 보고 데이터가 유효하다고 판정 |
| 5 | 라이브 URL·배포 로그·대시보드 헬스체크 | 실제 사용자 영향과 배포 결과 확인 | 로컬 빌드 성공만으로 라이브 성공 판정 |
| 6 | Telegram 메시지와 일일 요약 | 운영자 알림 맥락 및 전달 상태 확인 | 알림 미수신을 발행 성공으로 해석 |

## 3. 표준 오류 이벤트 계약

모든 새 오류 기록은 아래 최소 필드를 가진다. `detail_redacted`에는 API 키, Authorization 헤더, 비밀번호, 전체 URL 쿼리, 개인 식별 정보를 저장하지 않는다.

| 필드 | 형식 | 에이전트 사용 규칙 |
|---|---|---|
| `event_id`, `occurred_at`, `run_id` | 식별자·UTC 시각·실행 식별자 | 동일 실행의 중복 이벤트를 `fingerprint`와 함께 묶는다. |
| `blog_id`, `pipeline`, `stage` | 문자열 | 블로그·실행 경로·오류 단계를 반드시 분리한다. |
| `problem_id`, `reason`, `severity` | 표준 코드·원인 키·등급 | `reason`은 기계 판독용, `problem_id`는 운영 정책용으로 유지한다. |
| `retryable`, `attempt`, `max_attempts` | 불리언·정수 | 재시도는 이 값과 실제 부작용 여부를 함께 확인한 뒤 수행한다. |
| `source_name`, `http_status`, `timeout_seconds` | 외부 의존성 증거 | 소스/API 문제와 내부 코드 문제를 구분한다. |
| `detail_redacted`, `fingerprint` | 정제된 상세·해시 | 상세 오류를 설명하되 민감정보를 노출하지 않는다. |
| `state` | `open`, `acknowledged`, `resolved`, `suppressed` | 해결 전에는 `resolved`로 바꾸지 않는다. |
| Telegram 감사 | 전송 성공, HTTP 상태, 메시지 ID, 정제 본문 | 발행 오류와 알림 전달 오류를 분리한다. |

## 4. 에이전트 의사결정 알고리즘

에이전트는 새 이벤트마다 다음 순서를 지킨다. 이 절차는 수정 행위보다 진단과 안전 게이트를 우선한다.

```text
1. 이벤트 유효성 확인
   - 필수 필드, 실행 시각, 동일 fingerprint의 최근 반복, 대시보드 신호를 확인한다.
2. 실제 영향 판정
   - 발행·배포·사용자 노출·데이터 손상 중 하나가 실제로 발생했는지 확인한다.
3. 오탐·정상 제어 흐름 배제
   - quota, already_running, 품질 게이트, 검사기 결함, 오래된 요약을 분리한다.
4. 분류 확정
   - 표준 P 코드와 stage를 부여하고, 불명확하면 unknown_failure로 기록한다.
5. 수정 권한 판정
   - 자동 수정 허용 목록인지, 파일럿·테스트·사람 승인이 필요한지 결정한다.
6. 최소 수정 실행
   - 영향 파일을 최소화하고, 설정·DB·외부 서비스 변경은 분리한다.
7. 검증
   - 재현 테스트, 관련 단위 테스트, dry run, 라이브 확인을 순서대로 수행한다.
8. 종료 기록
   - 증거·변경 파일·테스트·라이브 결과·잔여 위험을 이벤트와 작업 기록에 남긴다.
```

## 5. 자동 수정·승인 경계

에이전트는 "수정 가능"과 "수정 후 외부 반영 가능"을 분리해야 한다. 로컬 코드 수정이나 테스트 추가는 가능해도, 원격 배포·발행·결제·권한 변경은 별도 승인이 필요하다.

| 조치 | 기본 권한 | 필수 검증 | 사람 승인 필요 |
|---|---|---|---|
| 로그·DB·설정의 읽기 전용 조사 | 자동 | 없음 | 아니오 |
| 테스트 추가, parser·검사기 버그의 최소 코드 수정 | 자동 | 재현 테스트 + 관련 회귀 테스트 | 원격 푸시 전 필요 |
| 재시도 가능한 수집 작업의 dry run | 자동 | 외부 부작용 없음 확인 | 아니오 |
| 데이터 수집 재시도 | 조건부 | idempotency, duplicate guard, rate limit 확인 | 대량 실행이면 필요 |
| 스케줄러·대시보드 재시작 | 조건부 | 진행 중인 발행·하위 프로세스 확인 | 진행 중 작업을 중단하면 필요 |
| 코드 커밋·원격 푸시 | 조건부 | diff, 테스트, 포함 파일 확인 | 항상 필요 |
| 실제 발행·재발행·배포 | 제안만 | 콘텐츠·도메인·배포 대상 확인 | 항상 필요 |
| 삭제, DB 대량 갱신, DNS·권한·토큰 변경 | 금지 | 해당 없음 | 항상 필요 |
| 기준 완화, duplicate guard 우회, 검사 비활성화 | 금지 | 원인·대안·영향 분석 | 항상 필요 |

## 6. 오류와 경고의 상태 전이

| 상태 | 의미 | 허용 행동 | 종료 조건 |
|---|---|---|---|
| `open` | 새 오류이며 아직 원인이 확정되지 않음 | 증거 수집, 분류, 재현 | 원인 확인 또는 억제 사유 확인 |
| `acknowledged` | 운영자가 인지했고 조사 중임 | 파일럿 수정, 테스트, 제한적 재시도 | 검증된 해결 또는 보류 결정 |
| `resolved` | 원인이 해결됐고 재현·라이브 검증을 통과함 | 사후 모니터링 | 동일 fingerprint 재발 시 새 `open` 생성 |
| `suppressed` | 정상 제어 흐름 또는 의도적 중단임 | 요약 집계만 | 기준 변경 또는 새로운 증거 발생 |

`resolved`는 코드가 바뀌었다는 사실이 아니라 **문제 재현이 실패하고 영향 경로가 정상임이 검증된 상태**를 의미한다.

## 7. 대시보드 신호별 공통 진단 규칙

| 신호 종류 | 우선 확인 | 흔한 오판 | 수정 방향 |
|---|---|---|---|
| 대량 `fail` | 실패율, 공통 검사기, 실제 라이브 샘플 | 검사기 정규식·홈페이지 전용 검사 오류 | 검사기 보정 후 표본·전수 재검증 |
| 전부 `pass` | 검사 대상 DB·컬럼·상태값, 예외 삼킴 | graceful pass를 정상으로 해석 | 연결·상태값 보정, 무력 검사로 표기 |
| 반복 `no_result` | 후보 수, 발행 이력, 필터, 소스 응답 | 후보 소진과 일시 API 공백 혼동 | P26/P27 분리 후 제한 재시도 또는 재고 확충 |
| 중복 guard | source_id/slug/title, 직전 실행 상태 | 중복 차단을 시스템 실패로 취급 | 중복 데이터 정리; guard 우회 금지 |
| stale·freshness | 실제 발행 일정, 데이터 유효 기간, 외부 이벤트 날짜 | 과거 요약을 현재 장애로 해석 | 데이터 갱신 작업으로 큐화 |
| validation defect | 검사 함수, 입력 형태, 예외 처리 | 콘텐츠 결함으로 오진 | 검사기를 별도 수정하고 과거 결과 재평가 |
| Telegram 미수신 | 감사 기록, HTTP 상태, bot 권한 | 발행 실패와 알림 실패 혼동 | P31로 분리하여 자격·권한·API 확인 |

## 8. 안전한 수정 표준

에이전트는 다음 품질 게이트를 통과하지 못하면 수정안을 "제안"으로만 남기고 자동 반영하지 않는다.

1. **재현성:** 실제 오류 또는 축소된 테스트로 수정 전 실패를 재현한다.
2. **최소성:** 수정 라인마다 특정 오류·테스트·증거와 직접 연결돼야 한다.
3. **부작용 분석:** 중복 발행, 콘텐츠 손실, 배포 잠금, 외부 API 비용 증가 여부를 명시한다.
4. **검증:** 단위 테스트, 해당 파이프라인 테스트, 필요 시 dry run과 라이브 확인을 순서대로 실행한다.
5. **가역성:** 배포 전에는 롤백 가능한 커밋·설정 백업·변경 목록을 남긴다.
6. **기록:** 이벤트 `state`, 근거 링크/경로, 변경 커밋, 테스트 결과, 잔여 위험을 기록한다.

## 9. 에이전트 작업 지시 템플릿

다른 에이전트에게 오류 처리를 맡길 때 아래 형식을 사용한다.

```markdown
대상 이벤트: <event_id 또는 problem_id + blog_id>
목표: 원인 판정과 최소 수정. 외부 발행·배포·푸시는 승인 전 수행하지 말 것.
증거: <대시보드 API 응답, 로그 경로, 실행 ID>
필수 절차:
1. 동일 fingerprint의 최근 이벤트와 실행 로그를 확인한다.
2. 정상 제어 흐름·오탐·실제 장애를 구분한다.
3. 원인 가설과 반증 방법을 최소 1개씩 제시한다.
4. 수정이 필요하면 재현 테스트를 먼저 작성하거나 기존 테스트를 선택한다.
5. 최소 diff를 적용하고 관련 테스트·dry run을 실행한다.
6. 변경 파일, 테스트 결과, 라이브 영향, 사람 승인 필요 여부를 표로 보고한다.
금지: duplicate guard 우회, 검사 비활성화, 데이터 삭제, 재발행·배포·푸시, 비밀값 노출.
```

## 10. 문서·레지스트리 변경 규칙

새 오류가 발견되면 에이전트는 바로 임의 코드 번호를 만들지 않는다. 먼저 `unknown_failure`로 기록하고 다음 정보를 확보한다.

| 항목 | 요구사항 |
|---|---|
| 발생 조건 | 최소 1개의 재현 가능한 입력 또는 로그 패턴 |
| 영향 | 발행·배포·데이터·알림 중 어떤 경로에 영향을 주는지 |
| 구분 근거 | 기존 P 코드와 겹치지 않는 이유 |
| 심각도 | 사용자 영향, 자동 복구 가능성, 데이터 손상 가능성 |
| 재시도 정책 | idempotency와 rate limit을 고려한 한계값 |
| 해결 검증 | 테스트, dry run, 라이브 확인 중 필요한 조합 |
| 승인 수준 | 자동 수정·제안만·사람 승인 중 하나 |

오탐·미탐은 사건으로 기록할 수 있으나, 심각도 승격·규칙 비활성화·기준 완화는 사람 승인 없이 수행하지 않는다.

## 11. 반드시 기억할 특이점

대시보드가 보이는 신호를 모두 즉시 고쳐야 하는 것은 아니다. `quota`와 `already_running`은 흔히 정상 제어 흐름이며, 중복 guard는 발행 보호 장치다. 또한 같은 검사가 다수 블로그에서 동시에 실패하면 콘텐츠를 대량 수정하기 전에 검사기·입력 형식·라이브 샘플을 먼저 점검해야 한다. 반대로 모든 블로그가 통과하는 검사는 연결된 데이터베이스와 상태값이 실제로 검사되고 있는지 의심해야 한다.

에이전트의 성공 기준은 경고 수를 0으로 만드는 것이 아니라, **실제 장애는 빠르게 복구하고 정상 제어 흐름·오탐은 명확히 분리하며, 수정이 새로운 발행·배포 위험을 만들지 않는 것**이다.
