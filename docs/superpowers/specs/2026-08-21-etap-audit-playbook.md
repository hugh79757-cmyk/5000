## 1. Why this exists

ETAP has 35 Hugo blogs (`config/blogs.d/etap.yaml`, 802 lines) generated by
the `etap` pipeline. Before any remediation, we need a reproducible audit that
runs the same 3-layer rule model the rest of the 5000 fleet uses, but grouped
by **content family** so that one representative per family carries the load.

This playbook defines:

1. The **13-family map** (how the 35 blogs collapse into 13 audit groups).
2. The **harness** (existing code that actually evaluates rules).
3. `scripts/etap_audit.py` — the audit driver and its 3 modes.
4. The **methodology**: *layer 3 times + family representative 13 times*.

## 4. `scripts/etap_audit.py` — the audit driver

> If the file does not yet exist, this section is the spec TAP implements.
> The interface below is the contract; the harness in §3 does the real work.

### 4.1 Three modes

| Mode | What it audits | Input source |
|------|---------------|--------------|
| `template` | Each post's frontmatter + body structure vs `ETAP-BODY-STANDARD.md` and `config/quality_checklist.yaml:578-598`. | `content/posts/*/index.md` under each blog `site_path`. |
| `corpus` | Fleet-wide scan of all posts for leakage (CJK/CoT), broken featureimage, forbidden tokens, duplicate slugs. | All `site_path/content/posts/**/index.md` across the 35 blogs. |
| `feed` | Live-site output validation — rendered HTML/compliance after deploy (adsense slots, GA4, TOC off). | Live `domain` (e.g. `adventure.techpawz.com`) or built `public/`. |

### 4.2 Common parameters

```
python3 scripts/etap_audit.py \
  --mode {template,corpus,feed} \
  --family {ADVENTURE,...,DEALS|ALL} \   # default ALL = all 13
  --blog   {blog_id} \                    # optional single-blog override
  --config config/blogs.d/etap.yaml \
  --rules  config/rules.yaml \
  --checklist config/quality_checklist.yaml \
  --out    ./audit_out \                  # output dir (CSV + markdown)
  --conn   ops_dashboard/ops.db           # for get_blog_brand / master table read
```

- `--family ALL` walks all 13 families; `--family ADVENTURE` runs only that
  family's **representative** blog (methodology in §5).
- `--blog` bypasses the family map and audits one explicit blog.

### 4.3 Output

For each run the script writes **two artifacts** into `--out`:

1. **CSV** — `etap_audit_{mode}_{family|ALL}_{YYYYMMDD}.csv`
   - Columns: `blog_id, family, scope(global|family|blog), rule_code,
     severity, passed(bool), detail`
   - One row per (blog × resolved rule). This is the machine-readable master
     table.
2. **Markdown** — `etap_audit_{mode}_{family|ALL}_{YYYYMMDD}.md`
   - Human summary: per-family pass rate, per-rule violation counts, top
     offenders, and a `DISCOVERY` banner (no fixes applied).

### 4.4 Master table reading method

The "master table" is the union of:

- **Local run table** — the CSV from §4.3 (one row per blog×rule). Read it
  with any CSV reader; filter `passed == False` to get the violation backlog.
- **Live registry** — `ops_dashboard/registry/rules.py` `all_entries()` /
  `get_entry(id)` (`ops_dashboard/registry/rules.py:56-66`) is the canonical
  definition of every `rule_code` (R01–R12, THUMBNAIL-01, R2-01, FM-*, C08).
  Join the CSV `rule_code` column against `get_entry()` to resolve
  `severity`, `description`, and the linked `agent_action`.
- **Brand resolution** — to apply the `family` layer, call
  `resolve_rules_for_blog(rules, conn, blog_id)`
  (`shared/rule_hierarchy.py:122-137`), which internally uses
  `get_blog_brand(conn, blog_id)` (`ops_dashboard/db.py:1670`). ETAP blogs
  resolve to `brand = "etap"`.

Reading order for a TAP operator:
1. Open the Markdown summary → see family pass rates at a glance.
2. Open the CSV → filter `passed==False` → that is the work queue.
3. For each `rule_code` in the queue, `get_entry(code)` → get the fix action.

## 5. Methodology — "layer 3 times + family representative 13 times"

The audit is deliberately cheap and exhaustive at the same time:

- **layer 3 times** — every check is evaluated through all three rule
  scopes (`global`, `family=etap`, `blog`) using the precedence engine
  `resolve_rules` / `resolve_rules_for_blog`
  (`shared/rule_hierarchy.py:89-137`). A rule "passes" only if it passes at
  the effective (most specific) layer.
- **family representative 13 times** — instead of auditing all 35 blogs, the
  script audits the **representative blog** of each of the 13 families once
  (`--family ALL` runs exactly 13 representative blogs). Because all member
  blogs in a family share `theme: blowfish`, `language: en`, and the ETAP
  body standard, the representative's result is treated as the family's
  result. This collapses 35 blog evaluations into 13 representative
  evaluations while still touching every family.

Run matrix:
```
for family in 13 families:
    rep = REPRESENTATIVE[family]          # §2 table
    for scope in [global, family, blog]:  # layer 3 times
        evaluate(rep, scope)              # via resolve_rules_for_blog
```

If a representative fails, the whole family is flagged; individual member
blogs can later be deep-audited with `--blog <id>` (corpus/feed mode) only
where the representative surfaced a problem.

## 6. TAP quick-start (read this, then run)

1. **Understand the map** — §2 (13 families, representatives).
2. **Pick a mode** — `template` (structure), `corpus` (leakage/integrity),
   `feed` (live compliance). Start with `template`.
3. **Run the representative sweep**:
   ```
   python3 scripts/etap_audit.py --mode template --family ALL \
     --config config/blogs.d/etap.yaml --rules config/rules.yaml \
     --checklist config/quality_checklist.yaml --out ./audit_out \
     --conn ops_dashboard/ops.db
   ```
4. **Read results** — §4.4 (Markdown summary → CSV queue → `get_entry`
   for fix actions).
5. **Escalate, don't fix** — this is `DISCOVERY`. Record findings; remediation
   is a separate (non-discovery) phase.
